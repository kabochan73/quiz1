# 04. イテレーション計画

「2〜3回作り直しながらブラッシュアップ」する前提で、各周回のゴールと学びを整理する。
毎回ゼロから作り直すのではなく、**前の周回の設計ドキュメントを更新してから実装** する。

## v1 — 基礎固め（今ここ）

**ゴール**: 王道の Laravel + Blade で、記述回答の AI 採点が一通り動く。

- 認証（Breeze）
- 問題 CRUD + ルーブリック + カテゴリ / タグ
- 記述回答 → キュー採点 → 部分点 + フィードバック表示
- 回答履歴 一覧 / 詳細
- 簡易ダッシュボード（カテゴリ別平均、点数推移）
- Pest テスト、Larastan、Pint

**この周回で身につけること**
- Eloquent リレーション（1対多、多対多、中間テーブル、スナップショット）
- FormRequest / Policy / キュー / Job
- 外部 API を差し替え可能な形でサービス層に閉じ込める設計
- 構造化出力の受け取りとバリデーション

**振り返りで見る観点**
- 採点結果は納得できるか？ ブレるか？
- モデル層・サービス層の責務分割は妥当だったか？
- Blade + Alpine で UX はどこが苦しいか？（→ v2 の技術判断材料）

---

## v2 — UX と採点品質

**ゴール**: 「使っていて気持ちいい」と「採点が信頼できる」を上げる。

- **画面**: Blade のつらみ次第で **Livewire** または **Inertia + Vue/React** に移行を検討
- **リアルタイム採点結果**: ポーリングをやめて Laravel Echo + Reverb（WebSocket）
- **復習モード**: 弱点カテゴリ・低得点問題を優先出題。簡単な間隔反復（次回出題日）
- **ダッシュボード強化**: 観点別の弱点分析、正答率の推移グラフ
- **採点プロンプトの改善サイクル**
  - eval セットを用意（回答例 + 期待スコア帯）
  - プロンプト変更前後で採点のブレ・妥当性を比較
  - `prompt_version` を上げながら記録
- **ルーブリック作成の支援**: 採点はルーブリック品質に全依存するので、
  AI が問題文から観点＋配点のドラフトを提案 → ユーザーが調整、を入れる
- **参考解答の扱い強化**: 採点結果に「参考解答との差分」を表示、参考解答の信頼度表示
- **キュー**: database → Redis
- soft delete 導入（問題を消しても履歴を残す）

**この周回で身につけること**
- リアルタイム通信 / フロント技術の選定と移行
- LLM を組み込んだ機能の「評価」の回し方
- データ分析寄りのクエリ・集計

## v3 — 公開とプロダクション品質

**ゴール**: 他人に見せられる / 使ってもらえる状態にする。

- **共有機能**: 問題を公開し、他ユーザーが解ける。作者は他人の回答も閲覧可（任意）
- **API モード**: `/api` を整備（Sanctum）。SPA やモバイルから叩ける
- **AI プロバイダ抽象化**: `GraderInterface` に別実装を追加、設定で切替
- **パフォーマンス**: N+1 潰し、キャッシュ、採点のバッチ化
- **インフラ**: Docker 化、CI（GitHub Actions で test + Larastan + Pint）、デプロイ
- **監視**: 採点失敗率・レイテンシ・コストのダッシュボード

**この周回で身につけること**
- API 設計 / 認証トークン
- CI/CD、コンテナ、デプロイ
- 運用監視・コスト管理

## 作り直しの進め方（各周回共通）

1. 前周回の振り返りを `docs/` に追記（何が良かった / 何がつらかった）
2. 該当ドキュメント（01〜03）を更新 → 差分をレビュー
3. 新しいブランチで実装
4. 動作確認 → 振り返り → 次周回へ
